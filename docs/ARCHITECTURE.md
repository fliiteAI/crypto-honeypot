# Architecture Overview: Crypto Wallet Honeypot

This document describes the architectural design, detection strategy, and security philosophy of the Crypto Wallet Honeypot system.

## Detection Strategy: The 4-Layer Defense

The system employs a multi-layered detection strategy to ensure that an attacker is caught at multiple stages of their lifecycle, from initial discovery to successful exfiltration and use of stolen assets.

### Layer 1: File Integrity Monitoring (FIM)
The foundation of the honeypot is Wazuh's FIM capability. We deploy realistic-looking cryptocurrency wallet files (e.g., `wallet.dat`, `keystore`, `id.json`) in standard locations where attackers and malware expect to find them.
- **Mechanism:** Wazuh `syscheck` monitors these files for any read, modification, or deletion.
- **Detection:** Triggers immediately when a file is touched. High-fidelity `whodata` monitoring (via `auditd` on Linux) identifies the specific user and process responsible.

### Layer 2: Process & Command Auditing
Going beyond simple file access, this layer monitors the *behavior* around the honeypot.
- **Mechanism:** Integration with Linux `auditd` and Windows Sysmon.
- **Detection:** Identifies suspicious patterns like rapid sequential access to multiple wallet paths (indicative of an automated infostealer) or the use of filesystem enumeration tools (e.g., `find`, `dir`, `Get-ChildItem`) targeting honeypot directories.

### Layer 3: Network Correlation
This layer correlates honeypot file access with network activity to identify exfiltration.
- **Mechanism:** Wazuh rules analyze process activity and DNS queries following a honeypot trigger.
- **Detection:** Detects if a process that accessed a honeypot file subsequently uses network tools (e.g., `curl`, `scp`, `powershell`) or resolves domains associated with exfiltration (e.g., `pastebin.com`, `transfer.sh`). It also monitors for the creation of archives (ZIP, TAR) which often precedes exfiltration.

### Layer 4: On-Chain Monitoring
The final layer tracks the actual use of the "stolen" credentials.
- **Mechanism:** External block explorer watchlists (via `honeypot-deployer export-addresses`).
- **Detection:** Alerts when the honeypot addresses are queried for balance, used in a transaction, or targeted by a DeFi drainer (token approval). This provides definitive proof of a successful theft and helps track the attacker's footprint on the blockchain.

## Security Philosophy: Zero False Positives

The system is designed with a **zero false positive** philosophy. In a standard production environment, there is no legitimate reason for a user or a system process to access the specific paths and files generated by the `honeypot-deployer`.

- **Intentionality:** Every access to a honeypot file is treated as a high-severity security event.
- **Fidelity:** By focusing on specific, non-functional assets, we eliminate the "noise" typically associated with FIM on active system files.
- **Automation:** The use of randomized content and names (via the CLI) prevents attackers from easily identifying the honeypot through static signatures.
