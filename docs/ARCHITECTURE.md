# Architecture Overview: Crypto Wallet Honeypot

The Crypto Wallet Honeypot system is a multi-layered defensive tool designed to detect, attribute, and alert on unauthorized access to cryptocurrency-related artifacts on monitored endpoints.

## Design Philosophy: "Zero False Positives"

The core of the system is built on a "zero false positive" design philosophy. In a production environment, there is no legitimate reason for any user or authorized process to access, read, or modify the honeypot files generated by this tool. Therefore, any interaction with these artifacts is treated as a high-fidelity indicator of malicious activity, ranging from automated infostealer malware to manual lateral movement by an intruder.

## 4-Layer Detection Strategy

The system utilizes four distinct layers of detection to provide comprehensive visibility into the attacker's actions.

### Layer 1: File Integrity Monitoring (FIM)
- **Mechanism:** Wazuh FIM (syscheck).
- **Function:** Monitors the honeypot files (e.g., `wallet.dat`, `id.json`, `keystore`) for any access (read), modification, or deletion.
- **Goal:** Provide the initial alert that a honeypot has been touched.

### Layer 2: Process & Command Auditing
- **Mechanism:** Linux `auditd` and Windows Sysmon.
- **Function:** Captures the specific process, user, and command-line arguments used to access the honeypot artifacts.
- **Goal:** Identify the tool used by the attacker (e.g., `cat`, `powershell`, or a custom malware binary) and provide user attribution.

### Layer 3: Network Correlation
- **Mechanism:** Wazuh log analysis correlating Layer 2 events with network activity.
- **Function:** Detects exfiltration-associated behavior immediately following a honeypot access event, such as using `curl` to upload data, or DNS queries to paste sites (e.g., `pastebin.com`).
- **Goal:** Confirm the exfiltration phase of an attack.

### Layer 4: On-Chain Monitoring
- **Mechanism:** External block explorer watchlists (via `honeypot-deployer export-addresses`).
- **Function:** Monitors the blockchain for any activity (balance queries, transfers) involving the public addresses associated with the generated honeypot private keys.
- **Goal:** Detect if an attacker has successfully exfiltrated the keys and is attempting to use or sweep the funds on-chain, even if the endpoint monitoring was bypassed or logs were cleared.

## MITRE ATT&CK Mapping

The system's detections are mapped to several MITRE ATT&CK techniques, providing context for security teams.

| Technique ID | Name | Description |
|--------------|------|-------------|
| **T1083** | File and Directory Discovery | Attacker scanning for wallet files or seed phrases. |
| **T1005** | Data from Local System | Accessing and reading wallet files from the local filesystem. |
| **T1555** | Credentials from Password Stores | Specifically targeting cryptocurrency wallet storage. |
| **T1555.003** | Credentials from Web Browsers | Accessing browser extension local storage for wallets like MetaMask. |
| **T1560** | Archive Collected Data | Staging wallet files into a ZIP or TAR archive before exfiltration. |
| **T1041** | Exfiltration Over C2 Channel | Using existing C2 channels to move stolen wallet data. |
| **T1048** | Exfiltration Over Alternative Protocol | Using `curl`, `scp`, or webhooks to move stolen data. |
| **T1657** | Financial Theft | The final stage where stolen keys are used to move funds on-chain. |
| **T1070** | Indicator Removal | Attacker deleting the honeypot files after access to hide their activity. |
