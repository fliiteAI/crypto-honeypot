# Architecture Overview: Crypto Wallet Honeypot

This document describes the design and detection strategy of the Crypto Wallet Honeypot system.

## 4-Layer Detection Strategy

The system utilizes a multi-layered approach to ensure high-fidelity detection and correlation of attacker activity.

### Layer 1: Wazuh FIM (File Integrity Monitoring)
The foundation of the system is Wazuh's FIM module (syscheck). By deploying realistic wallet artifacts in standard locations, we create high-value targets for attackers. Any read, modification, or deletion of these files triggers an immediate alert.
- **Goal:** Real-time detection of honeypot file access.
- **Attributes:** `whodata="yes"`, `realtime="yes"`.

### Layer 2: Process & Command Auditing
On Linux, we utilize `auditd` to track the exact process and user that accessed the honeypot files. On Windows, we use `Sysmon` for similar process-level visibility.
- **Goal:** Identify *how* the files were accessed and by whom.
- **Example:** Detects if `curl` or a Python script was used to read a private key.

### Layer 3: Network Correlation
Wazuh rules correlate honeypot access with network-capable processes (e.g., `curl`, `scp`, `nc`) or DNS queries to known exfiltration sites (e.g., Pastebin, webhook.site).
- **Goal:** Detect exfiltration attempts following honeypot access.

### Layer 4: On-Chain Monitoring
The most definitive proof of a compromise is seeing the honeypot's public address being queried or used on-chain. We export these addresses to external block explorer watchlists for real-time monitoring.
- **Goal:** Confirm the attacker has successfully imported and is attempting to drain the "funds".

## MITRE ATT&CK Mapping

The following table maps the honeypot's detection capabilities to the MITRE ATT&CK framework.

| Technique ID | Technique Name | Detection Layer | Description |
|--------------|----------------|-----------------|-------------|
| **T1083** | File and Directory Discovery | Layer 1, 2 | Attacker listing files or searching for wallet paths. |
| **T1005** | Data from Local System | Layer 1 | Attacker reading honeypot wallet artifacts. |
| **T1555** | Credentials from Password Stores | Layer 1 | Accessing localized wallet files (e.g., `wallet.dat`). |
| **T1555.003** | Credentials from Web Browsers | Layer 1 | Accessing browser extension data folders. |
| **T1560** | Archive Collected Data | Layer 2, 3 | Using `zip` or `tar` on honeypot files before exfil. |
| **T1041** | Exfiltration Over C2 Channel | Layer 3 | Using known network tools to transmit stolen keys. |
| **T1048** | Exfiltration Over Alternative Protocol | Layer 3 | Sending data to paste sites or webhooks. |
| **T1657** | Financial Theft | Layer 4 | On-chain activity (transfers, approvals) using stolen keys. |
| **T1070** | Indicator Removal | Layer 1 | Attacker deleting the honeypot files after access. |

## Detection Rule Philosophy
The system is designed with a **Zero False Positive** philosophy. Because no legitimate user or process should ever access these honeypot paths during normal operations, any alert generated by this system is considered high-fidelity and requires immediate investigation.
