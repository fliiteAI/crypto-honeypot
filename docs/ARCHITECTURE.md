# Architecture Overview: Crypto Wallet Honeypot

The Crypto Wallet Honeypot system implements a multi-layered defense-in-depth strategy to detect and track attackers who target cryptocurrency assets. By deploying realistic but non-funded "bait" artifacts, the system creates high-fidelity alerts with zero false positives.

## 4-Layer Detection Strategy

The system is organized into four distinct detection layers, each targeting a different stage of an attacker's lifecycle.

### Layer 1: File Integrity Monitoring (FIM)
**Mechanism:** Wazuh FIM (syscheck)
**Description:** The first line of defense. It monitors the honeypot files themselves for any access (read), modification, or deletion.
*   **Linux:** Utilizes `auditd` for `whodata` monitoring to provide user attribution (who accessed the file).
*   **Windows:** Monitors standard wallet paths using the Wazuh agent's built-in FIM capabilities.

### Layer 2: Process & Command Auditing
**Mechanism:** Linux Auditd / Windows Sysmon
**Description:** Monitors the *behavior* around the honeypot files. It detects which processes are interacting with the honeypot paths and identifies common attacker tools.
*   **Detections:** Use of `find`, `grep`, `ls`, or `Get-ChildItem` on honeypot directories.
*   **Heuristics:** Detects rapid sequential access to multiple different wallet types (a hallmark of automated infostealer malware).

### Layer 3: Network Correlation
**Mechanism:** Wazuh Analysis Engine
**Description:** Correlates honeypot file access with subsequent network activity.
*   **Detections:** Network-capable processes (e.g., `curl`, `scp`, `powershell`) accessing a honeypot file.
*   **Exfiltration:** Detects DNS queries to known "paste" sites or file upload services immediately following honeypot access.

### Layer 4: On-Chain Monitoring
**Mechanism:** Blockchain Watchlists / Chain Monitor
**Description:** The final layer of detection that tracks the movement of the "stolen" assets on the blockchain.
*   **Mechanism:** Public addresses generated by the honeypot are added to watchlists (e.g., Etherscan, Solscan).
*   **Detections:** Any activity on the generated addresses (balance queries, transfers, token approvals) indicates that the attacker has successfully imported the stolen keys into a wallet.

The system's detections are mapped to confirmed MITRE ATT&CK techniques, providing clear context for security analysts.

| Technique ID | Technique Name | Detection Layer |
|--------------|----------------|-----------------|
| **T1083** | File and Directory Discovery | Layer 1, 2 |
| **T1005** | Data from Local System | Layer 1 |
| **T1555** | Credentials from Password Stores | Layer 1 |
| **T1555.003** | Credentials from Web Browsers | Layer 1 |
| **T1560** | Archive Collected Data | Layer 2 |
| **T1041** | Exfiltration Over C2 Channel | Layer 3 |
| **T1048** | Exfiltration Over Alternative Protocol | Layer 3 |
| **T1657** | Financial Theft | Layer 4 |
| **T1070** | Indicator Removal | Layer 1 |

## Component Interaction

1.  **Honeypot Deployer (CLI):** Generates randomized artifacts and an encrypted manifest.
2.  **Wazuh Agent:** Monitors the filesystem and process activity on endpoints, sending events to the manager.
3.  **Wazuh Manager:** Processes events using custom decoders and rules, triggering alerts and optional active responses (e.g., forensic snapshots).
4.  **Chain Monitor:** Periodically checks the status of honeypot addresses on-chain and feeds events back into Wazuh via the API or log analysis.
