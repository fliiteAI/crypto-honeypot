# Architecture Overview: Crypto Wallet Honeypot

This document describes the design principles, detection strategy, and MITRE ATT&CK mapping for the Crypto Wallet Honeypot system.

## Design Principles

1.  **Zero False Positives:** Honeypot files are placed in locations that legitimate users or processes should never access. Any interaction is considered malicious.
2.  **High Fidelity:** By combining filesystem monitoring with process auditing and on-chain tracking, we achieve high-confidence alerts.
3.  **Cross-Platform:** The system supports both Linux and Windows endpoints, common targets for crypto-focused attackers.
4.  **Stealth:** Artifacts are designed to look like authentic wallet files (Berkeley DB, JSON Keystores, LevelDB logs) to deceive both manual intruders and automated infostealers.

## 4-Layer Detection Strategy

The system utilizes a multi-layered approach to ensure detection even if one layer is bypassed or disabled.

### Layer 1: Wazuh FIM (Filesystem Integrity Monitoring)
The foundation of the system. Wazuh monitors honeypot paths for `read`, `write`, `delete`, and `attribute` changes.
- **Detection:** Immediate alert when a file is touched.
- **Wazuh Rule IDs:** 100501 (Accessed), 100502 (Modified), 100503 (Deleted).

### Layer 2: Process Auditing (Auditd / Sysmon)
Provides context to the filesystem access. It identifies *which* process and *which* user accessed the honeypot.
- **Linux:** Uses `auditd` rules with `whodata` to attribute file access to specific PIDs and UIDs.
- **Windows:** Uses `Sysmon` to track process creation and file access events.
- **Detection:** Identifies if the access was via a shell (`bash`, `powershell`), a network utility (`curl`, `scp`), or a known infostealer process.

### Layer 3: Network Correlation
Monitors for exfiltration activity occurring shortly after honeypot access.
- **Mechanism:** Wazuh correlates file access events with outbound network connections or the use of archival tools (`tar`, `zip`).
- **Detection:** Rapid multi-file access followed by a connection to an external IP or a paste site.

### Layer 4: On-Chain Monitoring
The final layer of detection. Even if an attacker successfully exfiltrates the keys and bypasses all endpoint security, their activity is caught when they import the keys.
- **Mechanism:** Public addresses generated by the honeypot are added to watchlists on block explorers (Etherscan, Solscan, etc.).
- **Detection:** Any on-chain activity (balance queries, transfers) on a honeypot address triggers an alert.

## MITRE ATT&CK Mapping

The Crypto Wallet Honeypot covers several techniques used by attackers during the discovery, credential access, and exfiltration phases.

| ID | Technique | Detection Layer |
|----|-----------|-----------------|
| **T1083** | File and Directory Discovery | Layer 1, 2 |
| **T1005** | Data from Local System | Layer 1 |
| **T1555** | Credentials from Password Stores | Layer 1 |
| **T1555.003** | Credentials from Web Browsers | Layer 1 |
| **T1560** | Archive Collected Data | Layer 2, 3 |
| **T1041** | Exfiltration Over C2 Channel | Layer 3 |
| **T1048** | Exfiltration Over Alternative Protocol | Layer 3 |
| **T1657** | Financial Theft | Layer 4 |
| **T1070** | Indicator Removal | Layer 1 |

## Component Overview

### Honeypot Deployer (CLI)
A Python-based tool that:
1.  Generates realistic crypto artifacts (BTC, ETH, SOL, XRP, ADA, Seeds).
2.  Manages an encrypted `manifest.json` to track generated keys and addresses.
3.  Generates platform-specific Wazuh and Auditd configurations.

### Wazuh Manager
Centralized SIEM that:
1.  Receives logs from agents.
2.  Decodes events using custom regex patterns.
3.  Triggers alerts based on high-severity rules.
4.  Executes Active Response scripts for automated remediation.

### Wazuh Agent
Endpoint software that:
1.  Performs real-time FIM on honeypot paths.
2.  Integrates with `auditd` (Linux) and `Sysmon` (Windows).
3.  Securely transmits events to the Manager.
