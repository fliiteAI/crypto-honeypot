# Architecture Overview: Crypto Wallet Honeypot

The Crypto Wallet Honeypot system is designed to provide high-fidelity detection of attackers targeting cryptocurrency assets. It employs a multi-layered detection strategy to ensure that even the most stealthy intruders are identified.

## 4-Layer Detection Strategy

### Layer 1: File Integrity Monitoring (FIM)
At the core of the system is Wazuh's FIM module. We deploy realistic-looking cryptocurrency wallet files (e.g., `wallet.dat`, `keystore` files) across monitored endpoints. Any unauthorized access (read, write, or delete) to these files triggers an immediate, high-priority alert.
- **Principle:** Zero False Positives. Legitimate users and processes have no reason to access these hidden/decoy files.

### Layer 2: Process & Command Auditing
On Linux, we utilize `auditd` to monitor the specific system calls associated with honeypot file access. This allows us to capture the exact process name, PID, and user account responsible for the access. On Windows, Sysmon provides similar process-level visibility.
- **Detection:** Differentiates between manual user access (`cat`, `type`) and automated malware/infostealers.

### Layer 3: Network Correlation
Information-stealing malware often follows a pattern: search for sensitive files, archive them, and then exfiltrate them to a remote server. The honeypot system correlates file access events with network activity (e.g., DNS queries to paste sites, outbound connections via `curl` or `powershell`).
- **Detection:** Detects staging for exfiltration and actual data transmission.

### Layer 4: On-Chain Monitoring
The ultimate confirmation of a successful theft is when the attacker attempts to use the stolen (non-funded) keys on the blockchain. We monitor the public addresses associated with our honeypot artifacts using block explorers and watchlists.
- **Detection:** Real-time notification when a honeypot key is imported or used on-chain.

## MITRE ATT&CK Mapping

The honeypot system provides coverage for several MITRE ATT&CK techniques:

| Technique ID | Name | Description | Detection Layer |
|--------------|------|-------------|-----------------|
| **T1083** | File and Directory Discovery | Attacker scanning for wallet files. | Layer 1, 2 |
| **T1005** | Data from Local System | Attacker reading wallet data. | Layer 1 |
| **T1555** | Credentials from Password Stores | Attacker accessing seed phrase backups. | Layer 1 |
| **T1555.003** | Credentials from Web Browsers | Attacker accessing browser extension data. | Layer 1 |
| **T1560** | Archive Collected Data | Attacker zipping wallet files for exfil. | Layer 2, 3 |
| **T1041** | Exfiltration Over C2 Channel | Attacker sending data to C2 server. | Layer 3 |
| **T1048** | Exfiltration Over Alternative Protocol | Attacker uploading data to paste sites. | Layer 3 |
| **T1657** | Financial Theft | Attacker using stolen keys on-chain. | Layer 4 |
| **T1070** | Indicator Removal | Attacker deleting honeypot files. | Layer 1 |

## Design Philosophy

- **High Fidelity:** Every alert generated by the honeypot is an indicator of compromise (IoC).
- **Realistic Deception:** Artifacts mimic the exact structure and metadata of popular cryptocurrency wallets.
- **Privacy First:** Private keys are generated locally and stored securely in an encrypted manifest; they are never shared with the SIEM or any third party.
- **Lightweight:** Minimal impact on endpoint performance.
