# Architecture Overview: Crypto Wallet Honeypot

The Crypto Wallet Honeypot system is designed to detect and alert on unauthorized access to sensitive cryptocurrency credentials. It employs a "zero false positive" strategy, predicated on the fact that no legitimate user or process should ever access these specific honeyfiles.

## 4-Layer Detection Strategy

The system utilizes four distinct layers of detection to provide high-fidelity alerts and track attacker activity from initial discovery to on-chain theft.

### Layer 1: File Access Detection (FIM)
The foundation of the system is Wazuh's File Integrity Monitoring (FIM). We deploy realistic-looking cryptocurrency artifacts (wallet files, keystores, seed phrases) in standard locations.
- **Mechanism:** Wazuh `syscheck` monitoring with `whodata="yes"`.
- **Detection:** Any read, modify, or delete operation on a honeypot file triggers an immediate alert.

### Layer 2: Process & Command Auditing
Beyond just knowing a file was accessed, we want to know *how* and by *whom*.
- **Mechanism:** Linux `auditd` and Windows `Sysmon`.
- **Detection:** Captures the process name, command-line arguments, and user ID associated with the access. This helps distinguish between automated infostealers and manual attackers.

### Layer 3: Network Exfiltration Detection
Attackers often exfiltrate stolen credentials immediately after discovery.
- **Mechanism:** Correlation of FIM/Audit events with network activity (Wazuh integration).
- **Detection:** Alerts when a network-capable process (e.g., `curl`, `scp`) accesses a honeypot file, or when suspicious DNS queries (e.g., to paste sites or C2 servers) occur shortly after a honeypot access.

### Layer 4: On-Chain Monitoring
The ultimate confirmation of a successful attack is when the stolen keys are used on-chain.
- **Mechanism:** Block explorer watchlists and custom monitoring scripts.
- **Detection:** Alerts when activity is detected on the public addresses associated with the honeypot private keys (e.g., balance queries, token approvals, or transfers).

## MITRE ATT&CK Mapping

The system's detections are mapped to confirmed MITRE ATT&CK techniques:

| ID | Name | Description |
|---|---|---|
| **T1083** | File and Directory Discovery | Attacker scanning the filesystem for wallet artifacts. |
| **T1005** | Data from Local System | Attacker reading the honeypot wallet files. |
| **T1555** | Credentials from Password Stores | Accessing stored cryptocurrency credentials. |
| **T1555.003** | Credentials from Web Browsers | Accessing browser extension wallet data (e.g., MetaMask). |
| **T1070** | Indicator Removal | Attacker deleting honeyfiles to cover their tracks. |
| **T1560** | Archive Collected Data | Staging stolen wallet files in a compressed archive. |
| **T1041** | Exfiltration Over C2 Channel | Sending stolen keys to an attacker-controlled server. |
| **T1048** | Exfiltration Over Alternative Protocol | Exfiltrating data via paste sites or other channels. |
| **T1657** | Financial Theft | Using stolen keys to transfer funds on-chain. |

## Zero False Positive Philosophy

Most security alerts require investigation to determine if they are legitimate. This system is different:
- **No Legitimate Use:** There is no scenario where a regular user or authorized system process should read `~/.bitcoin/wallet.dat` if it was generated by this tool.
- **High Severity:** Because false positives are virtually non-existent, alerts from this system can be treated as high-priority, confirmed compromises, allowing for automated response actions (like host isolation).
