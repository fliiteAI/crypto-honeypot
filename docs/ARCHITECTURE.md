# Architecture Overview: Crypto Wallet Honeypot

This document describes the architectural design, detection strategy, and MITRE ATT&CK mapping for the Crypto Wallet Honeypot system.

## 4-Layer Detection Strategy

The system utilizes a multi-layered approach to ensure high-fidelity detection of attackers at various stages of their lifecycle.

### Layer 1: File Integrity Monitoring (FIM)
- **Mechanism:** Wazuh FIM (syscheck).
- **Goal:** Detect any interaction with honeypot wallet files.
- **Details:** Monitors specific paths where wallets are typically stored (e.g., `~/.bitcoin/wallet.dat`, `%APPDATA%\Ethereum\keystore`).
- **Fidelity:** Very High. Legitimate users and processes have no reason to access these hidden/decoy directories.

### Layer 2: Process & System Auditing
- **Mechanism:** Linux `auditd` and Windows Sysmon.
- **Goal:** Provide context on *who* and *how* the files were accessed.
- **Details:** Captures the Parent Process ID (PPID), Process ID (PID), User ID (UID), and the specific command line used to access the honeypot.
- **Detection Pattern:** Detects "infostealer" behavior, such as a browser process or a suspicious Python script reading multiple wallet directories in rapid succession.

### Layer 3: Network Correlation
- **Mechanism:** Wazuh log analysis & Network telemetry.
- **Goal:** Detect exfiltration attempts following honeypot access.
- **Details:** Correlates file access events with subsequent outbound network connections to known paste sites (Pastebin), cloud storage (Mega.nz), or common C2 patterns (curl/wget to external IPs).

### Layer 4: On-Chain Monitoring
- **Mechanism:** External blockchain watchers (via `honeypot-deployer export-addresses`).
- **Goal:** Detect when an attacker successfully exfiltrates and attempts to use the stolen keys.
- **Details:** Monitors the public addresses of the generated honeypots for any on-chain activity (balance queries, incoming transfers, or attempted outgoing transfers).
- **Fidelity:** Absolute. If a private key generated by this tool is used on-chain, it is a 100% confirmed compromise.

## MITRE ATT&CK Mapping

The Crypto Wallet Honeypot system maps to the following MITRE ATT&CK techniques:

| Technique ID | Name | Detection Layer |
|--------------|------|-----------------|
| **T1083** | File and Directory Discovery | Layer 1, 2 |
| **T1005** | Data from Local System | Layer 1 |
| **T1555** | Credentials from Password Stores | Layer 1 |
| **T1555.003**| Credentials from Web Browsers | Layer 1 |
| **T1560** | Archive Collected Data | Layer 2 |
| **T1041** | Exfiltration Over C2 Channel | Layer 3 |
| **T1048** | Exfiltration Over Alternative Protocol | Layer 3 |
| **T1657** | Financial Theft | Layer 4 |
| **T1070** | Indicator Removal | Layer 1 |

## Component Diagram

1. **`honeypot-deployer` CLI:** Generates artifacts and manages the encrypted manifest.
2. **Honeypot Artifacts:** Realistic files (BTC, ETH, SOL, etc.) placed on endpoints.
3. **Wazuh Agent:** Monitors artifacts via FIM and `auditd`/Sysmon.
4. **Wazuh Manager:** Processes events, applies rules, and triggers alerts/active response.
5. **Chain Monitor (Optional):** External service watching exported addresses for on-chain activity.
